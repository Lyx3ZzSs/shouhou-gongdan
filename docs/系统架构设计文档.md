## 1. 项目概述

### 1.1 业务背景

新能源行业售后服务渠道碎片化（400 电话、企业微信、邮件、小程序），业务复杂度高，跨部门协同频繁，工单量已超出人工处理能力。本平台通过 **AI 自动生成受理单 + 人工审核确认** 的协作模式，提升工单处理效率与质量。

### 1.2 核心功能

| 功能模块 | 说明 |
|---------|------|
| **工单审核工作台** | 三栏式专业审核界面，支持字段级 diff 对比、行内编辑、逐字段确认 |
| **工单队列管理** | 待审核工单列表，支持多维度筛选、排序、SLA 时效监控 |
| **审核决策引擎** | 确认通过 / 驳回 / 退回补充 / 转交复核多分支决策 |
| **字段级审计日志** | 记录每次字段变更的修改人、修改原因、前后值 |
| **Bad Case 回流** | 人工修正的字段自动入库，用于 AI 模型持续训练 |
| **分布式编辑锁** | 防止多人并发编辑同一工单，5 分钟 TTL 自动释放 |
| **乐观锁版本控制** | 防止并发提交导致数据覆盖 |
| **销售易同步** | 确认通过的工单同步至外部 CRM 系统 |

### 4.2 表结构详解

#### 4.2.1 `workorder` — 工单主表

| 分类 | 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|------|
| **主键** | `id` | VARCHAR(64) | PK | 工单唯一标识 |
| **审核追踪** | `version` | INTEGER | NOT NULL, DEFAULT 1 | 乐观锁版本号，每次审核 +1 |
| | `reviewed_at` | TIMESTAMP | NULL | 最近审核时间 |
| | `reviewed_by` | VARCHAR(64) | NULL | 最近审核人姓名 |
| | `reject_count` | INTEGER | NOT NULL, DEFAULT 0 | 累计驳回次数 |
| | `last_reject_reason` | TEXT | NULL | 最近驳回原因 |
| | `last_rejected_by` | VARCHAR(64) | NULL | 最近驳回人 |
| | `last_rejected_at` | TIMESTAMP | NULL | 最近驳回时间 |
| | `sync_status` | VARCHAR(16) | NOT NULL, DEFAULT 'pending' | 销售易同步状态 |
| **只读元数据** | `serial_number` | VARCHAR(64) | NULL | 工单流水号 |
| | `status` | VARCHAR(32) | NULL | 工单状态 |
| | `created_at` | TIMESTAMP | NULL | 创建时间 |
| | `initiator` | VARCHAR(64) | NULL | 发起人 |
| | `initiator_department` | VARCHAR(128) | NULL | 发起部门 |
| **可编辑字段 (28个)** | `station_name` ~ `required_solve_time` | VARCHAR/TEXT | NULL | AI 预填，人工可修改 |

> **备注**：ORM 模型仅定义审核所需的 35 列，实际生产库 workorder 表有 132+ 列。执行 `alembic revision --autogenerate` 会检测到缺失列并生成 DROP COLUMN，生产环境迁移必须使用手动编写的迁移脚本。

### 4.3 状态机

```mermaid
stateDiagram-v2
    [*] --> pending_review: AI 生成工单
    pending_review --> reviewing: 坐席获取编辑锁
    reviewing --> confirmed: 确认通过
    reviewing --> rejected: 驳回
    reviewing --> stashed: 暂存审核进度
    confirmed --> dispatching: 流转至派单系统
    rejected --> pending_review: 退回重新审核
    stashed --> reviewing: 恢复审核

    state confirmed {
        [*] --> sync_pending: 本地落库成功
        sync_pending --> synced: 销售易同步成功
        sync_pending --> sync_failed: 销售易同步失败(5s超时)
    }
```

### 5.2 接口详情

| 方法 | 路径 | 认证 | 锁保护 | 说明 |
|------|------|------|--------|------|
| `GET` | `/api/workorders` | JWT | 否 | 工单摘要列表（最近 50 条，按 created_at 降序） |

| `POST` | `/api/workorders/{id}/confirm` | JWT | **是** (423) | 确认提交 + 销售易同步 |
| `POST` | `/api/workorders/{id}/stash` | JWT | **是** (423) | 暂存审核进度 |
| `GET` | `/api/workorders/{id}/audit-logs` | JWT | 否 | 按 session 分组的变更历史 |
| `POST` | `/api/workorders/{id}/lock` | JWT | 否 | 获取分布式编辑锁 |
| `DELETE` | `/api/workorders/{id}/lock` | JWT | 否 | 释放锁（仅持有者可释放，403） |
| `PUT` | `/api/workorders/{id}/lock` | JWT | 否 | 心跳续期（仅持有者，锁丢失返回 423） |

## 6. 核心数据流

### 6.1 审核确认完整流程

```mermaid
sequenceDiagram
    actor User as 客服坐席
    participant FE as React 前端
    participant API as FastAPI 后端
    participant Lock as LockService (Redis)
    participant DB as PostgreSQL
    participant Audit as AuditService
    participant BC as BadCaseService
    participant XSY as 销售易 CRM

    Note over User,XSY: ═══ 阶段一：打开工单 ═══

    User->>FE: 1. 打开工作台
    FE->>API: GET /api/workorders (JWT)
    API->>DB: SELECT id, serial_number, status... LIMIT 50 ORDER BY created_at DESC
    DB-->>API: 工单摘要列表
    API-->>FE: WorkOrderSummary[]

    User->>FE: 2. 点击工单
    FE->>API: POST /api/workorders/{id}/lock
    API->>Lock: SET review_lock:{id} = operator_id NX EX 300
    Lock-->>API: OK (获取锁成功)
    API-->>FE: { locked: true, owner: "张三" }

    FE->>API: GET /api/workorders/{id}
    API->>DB: SELECT * FROM workorder WHERE id = {id}
    DB-->>API: WorkOrder 详情 (含 version)
    API-->>FE: WorkOrderResponse

    Note over User,XSY: ═══ 阶段二：逐字段审核 ═══

    loop 每个异常字段
        User->>FE: 3. 查看 AI 预填值
        alt 值正确
            User->>FE: 点击"确认"按钮
            FE->>FE: confirmField() → status=confirmed
        else 值需修改
            User->>FE: 4. 行内编辑 → 选择修改原因
            FE->>FE: setFieldValue() → status=modified → changeLog
        end
    end

    opt 自动暂存
        FE->>FE: useAutoSave: 1s 防抖 → dirty=true 时自动触发
        FE->>API: POST /api/workorders/{id}/stash
        API->>DB: UPDATE workorder SET status='stashed'
        API-->>FE: { status: "ok" }
    end

    Note over User,XSY: ═══ 阶段三：提交审核 ═══

    User->>FE: 5. 点击"确认提交"
    FE->>FE: 计算 effectiveChanges<br/>(currentValue ≠ originalValue 的字段)
    FE->>FE: 生成 idempotency_key (UUID v4)

    FE->>API: POST /api/workorders/{id}/confirm
    API->>API: 验证锁持有者 (lock_service.get_owner)

    critical 事务块 (BEGIN...COMMIT)
        API->>DB: 幂等检查: SELECT id FROM audit_log WHERE session_id = ?
        alt 已存在
            DB-->>API: 返回已有记录
            API-->>FE: { review_id: "dup", ... } (幂等返回)
        else 首次提交
            API->>DB: 乐观锁 UPDATE: SET status='confirmed', version=version+1<br/>WHERE id=? AND version=? AND status!='confirmed'
            alt version 不匹配
                DB-->>API: rowcount=0
                API-->>FE: HTTP 409 版本冲突
            else 更新成功
                API->>DB: 批量更新字段: UPDATE workorder SET field1=?, field2=?... WHERE id=?
                API->>Audit: batch_create(session_id, changes, operator)
                Audit->>DB: INSERT INTO audit_log (多条)
                API->>BC: batch_create(audit_log_ids, changes)
                BC->>DB: INSERT INTO bad_case_sample (多条)
            end
        end
    end

    API->>XSY: 同步至销售易 (5s 超时)
    alt 同步成功
        XSY-->>API: { external_id: "XSY-xxx" }
        API->>DB: UPDATE workorder SET sync_status='synced'
    else 超时/失败
        API->>DB: UPDATE workorder SET sync_status='failed'
    end

    API->>Lock: DEL review_lock:{id} (释放锁)
    API-->>FE: { status: "confirmed", sync_status: "synced", bad_case_count: 3 }

    FE->>FE: 更新队列（移除已审核工单）
    FE->>FE: 自动加载下一条工单（如果 openNext=true）
```

```mermaid
        API->>DB: 写入驳回审计日志<br/>INSERT INTO audit_log (field_path='/_rejected', change_type='rejected')
    end

    API->>API: 释放锁 (finally 块)
    API-->>FE: { status: "rejected", next_status: "pending_review" }
```

## 8. 关键设计模式

### 8.1 乐观锁版本控制

```mermaid
sequenceDiagram
    participant U1 as 坐席 A
    participant U2 as 坐席 B
    participant DB as PostgreSQL

    Note over U1,DB: 初始: version=1

    U1->>DB: 读取工单 (version=1)
    U2->>DB: 读取工单 (version=1)

    U1->>DB: UPDATE ... SET version=2 WHERE id=X AND version=1
    DB-->>U1: ✅ rowcount=1 (成功)

    U2->>DB: UPDATE ... SET version=2 WHERE id=X AND version=1
    DB-->>U2: ❌ rowcount=0 (版本冲突！)
    U2-->>U2: HTTP 409 → 弹出 VersionConflictDialog
```

**实现细节**：
- 每次审核确认/驳回时，`WHERE version = :expected_version` 作为 UPDATE 条件
- 冲突检测在 SQL 层面完成，无 TOCTOU 问题
- 前端收到 409 后弹出冲突解决弹窗，支持 merge（保留我的修改 + 拉取最新版本）或 discard（放弃我的修改 + 重新加载）

### 8.2 分布式编辑锁

```mermaid
sequenceDiagram
    participant U1 as 坐席 A
    participant API as FastAPI
    participant Redis as Redis
    participant U2 as 坐席 B

    U1->>API: POST /lock (获取锁)
    API->>Redis: SET review_lock:WO-001 "user_a:张三:2024-01-01T10:00:00" NX EX 300
    Redis-->>API: OK
    API-->>U1: { locked: true, owner: "张三" }

    U2->>API: POST /lock (尝试获取锁)
    API->>Redis: SET review_lock:WO-001 "user_b:李四:..." NX EX 300
    Redis-->>API: nil (key 已存在)
    API->>Redis: GET review_lock:WO-001
    Redis-->>API: "user_a:张三:2024-01-01T10:00:00"
    API-->>U2: { locked: false, owner: "张三", locked_minutes: 1 }

    loop 每 2 分钟心跳
        U1->>API: PUT /lock (心跳续期)
        API->>Redis: Lua Script: if get(key)==owner then expire(key, 300)
        Redis-->>API: 1 (续期成功)
    end

    Note over U1: 审核完成，提交
    U1->>API: POST /confirm
    API->>API: 审核逻辑...
    API->>Redis: Lua Script: if get(key)==owner then del(key)
    Note over Redis: 锁已释放
```

**实现细节**：
- 使用 Redis `SET key value NX EX 300` 实现原子获取
- 使用 Lua 脚本实现原子释放和心跳续期（消除 TOCTOU 竞态）
- 同一持有者重复获取时幂等返回（刷新 TTL）
- 审核提交后在 `finally` 块中释放锁（防止孤儿锁）
- 前端每 2 分钟发送心跳，后端 TTL 为 5 分钟

### 8.3 幂等性保证

```mermaid
flowchart TB
    REQ["收到审核请求<br/>(session_id=xxx)"]
    CHECK{"SELECT id FROM audit_log<br/>WHERE session_id = ?"}
    EXISTS["已存在 → 返回 dup<br/>不重复执行审核逻辑"]
    PROCEED["不存在 → 执行审核逻辑"]

    REQ --> CHECK
    CHECK -->|"结果存在"| EXISTS
    CHECK -->|"结果不存在"| PROCEED

    subgraph "审核事务块 (原子性)"
        VCHECK["乐观锁版本检查"]
        FUPDATE["字段批量更新"]
        ALOG["写入审计日志<br/>(session_id 作为幂等键)"]
        BC["写入 Bad Case"]
    end

    PROCEED --> VCHECK
    VCHECK --> FUPDATE
    FUPDATE --> ALOG
    ALOG --> BC
```

**实现细节**：
- `session_id` 由前端在初始化时生成（`crypto.randomUUID()`），整个审核会话内保持不变
- 后端在事务块内首先检查 `session_id` 是否已存在于 `workorder_audit_log` 表中
- 如果存在，直接返回幂等结果，不重复执行业务逻辑
- 销售易同步使用独立的 `idempotency_key`（每次提交时重新生成）

### 8.4 Bad Case 回流机制

```mermaid
flowchart LR
    AI["AI 模型<br/>自动填充工单字段"] -->|"AI 值"| WO["WorkOrder<br/>工单表"]
    WO -->|"坐席审核"| HUMAN["人工修正<br/>修改 AI 填充值"]

    HUMAN -->|"old_value (AI 值)"| BC["BadCaseSample<br/>ai_value / human_value"]
    HUMAN -->|"new_value (人工值)"| BC

    BC -->|"定时/批量导出"| TRAIN["模型训练集"]
    TRAIN -->|"fine-tune / RLHF"| AI

    style AI fill:#fce4ec,stroke:#c62828
    style BC fill:#fff3e0,stroke:#f57c00
    style TRAIN fill:#e8f5e9,stroke:#388e3c
```

**实现细节**：
- 仅在确认（confirmed）且有字段变更时触发 Bad Case 采集
- 将 `FieldChange.old_value` 映射为 `ai_value`，`FieldChange.new_value` 映射为 `human_value`
- 每条 Bad Case 通过 `audit_log_id` 外键关联到具体的审计日志记录
- `sample_status` 支持 pending / used / discarded 三种状态，用于下游训练流水线管理
- `source` 字段标识样本来源（当前为 `review_correction`）

### 8.5 前端切单竞态保护

```mermaid
sequenceDiagram
    participant User as 用户
    participant FE as 前端 Store
    participant API as 后端 API

    User->>FE: 快速点击工单 A
    FE->>FE: currentLoadId = 1
    FE->>API: fetchWorkOrder("A")

    User->>FE: 立即点击工单 B
    FE->>FE: currentLoadId = 2
    FE->>API: fetchWorkOrder("B")

    API-->>FE: 工单 A 的响应（较慢）
    FE->>FE: reqId(1) !== currentLoadId(2) → 丢弃！

    API-->>FE: 工单 B 的响应
    FE->>FE: reqId(2) === currentLoadId(2) → 渲染工单 B ✅
```

**实现细节**：
- `currentLoadId` 是一个单调递增计数器
- 每次 `loadTicketById()` 调用时递增，并记录当时的 `reqId`
- API 响应返回时检查 `reqId !== currentLoadId`，不匹配则丢弃过期响应
- 防止快速切单时旧请求覆盖当前工单数据

## 9. 安全与认证

### 9.1 认证流程

```mermaid
sequenceDiagram
    participant FE as 前端
    participant API as FastAPI
    participant JWT as JWT 引擎

    Note over FE: 开发阶段：硬编码 DEV_TOKEN<br/>生产阶段：OAuth2 登录获取

    FE->>API: GET /api/workorders<br/>Authorization: Bearer <token>

    API->>API: HTTPBearer 提取 token
    API->>JWT: jwt.decode(token, JWT_SECRET, HS256)
    JWT-->>API: { sub: "user_id", name: "张三", role: "customer_service_agent", department: "客服部" }

    alt role != "customer_service_agent"
        API-->>FE: HTTP 403 仅客服坐席可执行此操作
    else role 合法
        API-->>FE: 正常响应
    end
```

**安全措施**：
- JWT 使用 HS256 算法签名，密钥由环境变量 `JWT_SECRET` 注入
- 生产环境强制 JWT_SECRET >= 32 字符
- 角色鉴权：仅 `customer_service_agent` 角色可访问审核接口
- 编辑锁保护：审核/确认/暂存接口必须持有当前工单锁（423 Locked）
- 仅锁持有者可释放锁或续期（403 Forbidden）
