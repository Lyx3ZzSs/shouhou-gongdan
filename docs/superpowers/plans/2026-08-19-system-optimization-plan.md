# 售后工单审核平台优化实施计划

> 日期：2026-08-19  
> 依据：`2026-08-18-review-platform-redesign.md` 与当前代码审计  
> 原则：保持“6 个关键字段核对”定位；复用现有页面和后端能力；不新增依赖，不重建全量字段编辑器。

## 一、目标与上线门槛

目标是把当前演示/试点状态收敛为可上线的桌面审核平台：

1. 审核员能从概览进入 FIFO 队列，完成通过、修改后通过、驳回、跳过和恢复。
2. 6 个关键字段具备真实的场站与员工选择能力，派生字段自动更新。
3. 任何服务端阻断都必须可见，并提供“可修正”或“驳回上游”出口。
4. 原始对话、附件和客户/项目资料足以支撑人工判断。
5. 销售易同步异常能够安全人工处理。
6. 默认测试命令稳定通过，真实 PostgreSQL/Redis 集成测试不再静默跳过。

## 二、分阶段实施

### 阶段 0：测试与环境基线（0.5–1 天）

改动：

- `backend/pytest.ini` 增加 `testpaths = tests`，避免默认 `pytest` 收集并执行 `scripts/e2e_test.py`。
- 集成测试使用解析后的 host、port、user、password 参数连接 PostgreSQL，避免 URI 重编码造成密码认证失败。
- 集成测试连接失败改为明确失败；仅在显式环境开关下允许跳过。
- 对齐本地认证开关：开发环境前后端统一关闭或统一开启，生产构建默认开启 Keycloak。
- README 增加一条环境自检命令，覆盖 PostgreSQL、Redis 和 `/ready`。

验收：

- `pytest` 与 `pytest tests` 结果一致。
- PostgreSQL 集成测试 5 项实际执行通过，不再 skipped。
- Redis 锁测试实际执行通过。
- 前后端默认开发配置能够直接联调。

### 阶段 1：恢复完整导航与队列闭环（1–2 天）

改动：

- `PlatformNav` 恢复规格中的 6 个入口：概览、开始审核、稍后处理、工单搜索、审核统计、同步失败。
- 应用默认进入概览，复用现有 `Overview`、`WorkOrderModule` 和 `ReviewStats`。
- 修正关闭语义：关闭并放弃修改只删除草稿并释放锁，不改变工单状态；只有“跳过”才进入 `stashed`。
- 搜索页按工单号查询所有已审核状态，不再固定查询 `confirmed`。
- 增加最小的服务端“获取下一张”接口：按 FIFO 选择待审核且未被他人锁定的工单，并获取锁，避免客户端先加载队列首单再切换目标单。
- 恢复稍后处理时重新取锁；被占用时只读展示并允许继续跳过。

验收：

- 待审核 → 跳过 → 稍后处理 → 恢复 → 提交的状态链完整。
- 关闭并放弃后工单仍为原状态。
- 两名审核员并发点击“开始审核”不会拿到同一张工单。
- 导航中的每个入口均可到达、刷新后状态合理。

### 阶段 2：关键字段与核对证据（3–5 天）

改动：

- 场站编号改为现有台账数据的搜索选择；选中后自动带出项目名称，并在后端校验场站/项目一致性。
- 问题责任人改为北森员工缓存搜索；选中后自动带出问题责任部门，接口仍提交员工编码。
- 联系方式保留即时格式校验，服务端继续做最终校验。
- 审核页增加紧凑的“阻断问题”区域：
  - 6 个可编辑字段异常：定位到编辑器。
  - 其他系统字段异常：展示具体字段和原因，提供“驳回上游补充”操作，不开放 38 字段编辑。
- 实现 `review-context` 聚合接口，返回关键字段、其他字段、原始对话、附件索引、台账摘要、锁和版本。
- 附件提供文件名、类型、大小、预览/下载；原始对话保留时间、发言人和消息顺序。

验收：

- 场站、项目、责任人、责任部门不存在手工输入不一致。
- 任意后端 blocking issue 在页面上都有可理解说明和下一步操作。
- 审核员可在一个证据面板内核对对话、附件和台账。
- 关键字段修改仍只记录最终 AI 原值 → 人工最终值。

### 阶段 3：同步异常、统计与交付收口（2–3 天）

改动：

- 将同步失败页接入导航；用现有 Dialog 替代 `window.prompt`。
- `failed` 支持人工重试；`uncertain` 必须先确认“已创建/未创建”，并展示防重复建单提示。
- 人工对账操作写入审计日志，记录操作者、时间、外部工单号和结论。
- 概览只保留规格要求的核心指标：今日处理量、平均审核耗时、AI 字段修改率、驳回率，以及三个待办数量。
- 审核统计补最小时间范围筛选；复杂人员排名和大图表先保留但不继续扩展。
- 更新 README、用户手册和架构文档，删除旧三栏工作台、逐字段确认等过时描述。
- 增加一条真实 E2E：导入 → 取下一张并加锁 → 修改关键字段 → 暂存/恢复 → 确认 → 审计/Bad Case → 同步任务入队。

验收：

- 同步失败与不确定状态均有安全、可审计的人工出口。
- 概览数字与数据库抽查一致，指标口径在界面可见。
- 用户手册与实际页面逐项一致。
- 前端 typecheck、单测、构建，后端单测、PostgreSQL/Redis 集成和 E2E 全部通过。

## 三、建议任务拆分

| 批次 | 交付物 | 主要文件范围 | 可独立验收 |
|---|---|---|---|
| A | 测试与认证基线 | `backend/pytest.ini`、集成测试、前后端 env 示例、README | 是 |
| B | 导航与状态闭环 | `PlatformNav.tsx`、`App.tsx`、`WorkOrderModule.tsx`、审核 store/router | 是 |
| C | 场站/员工选择 | `KeyFieldReview.tsx`、查询 API、台账/员工缓存模型 | 是 |
| D | 阻断问题与证据 | 审核上下文 API、审核页、对话/附件读取 | 是 |
| E | 同步异常与文档 | 同步页、管理员 API、统计页、文档、E2E | 是 |

推荐按 A → B → C → D → E 顺序实施。B 完成后可先做内部试用；C、D、E 完成并通过 E2E 后再正式上线。

## 四、本轮明确不做

- 不恢复旧三栏 38 字段编辑器。
- 不新增工作流引擎、消息队列或新的状态管理库。
- 不建设独立手机审核流程；现阶段按规格保障 1280–1920 桌面端。
- 不扩展成本、备件、现场服务、客户回访等完整售后履约模块；另立项目评估。
- 不在没有数据需求前继续增加统计大屏和图表。

## 五、整体工作量

- 单人顺序实施：约 7–11 个开发日，加 2–3 个业务验收日。
- 若前后端并行：约 5–7 个工作日进入验收。
- 最大外部依赖：北森员工缓存数据质量、附件访问方式、原始对话数据结构、销售易测试环境。
